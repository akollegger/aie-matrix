# Implementation Plan: Human Participation as Ghost Peer

**Branch**: `030-human-ghost-peer` | **Date**: 2026-06-13 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/030-human-ghost-peer/spec.md`

## Summary

Treat the Intermedium browser client as a first-class ghost peer by adding a `human` role to the JWT credential system, issuing guest tokens via a new `POST /auth/guest` endpoint, granting a proximity exemption for directed `say()` calls from human callers, adding ghost-label broadcasting to Colyseus room state (enabling broker badging), and wiring the client to use unified MCP tool calls instead of the bespoke `/human-say` path.

## Technical Context

**Language/Version**: TypeScript 5.7 / Node.js 24 (ESM, `"type": "module"`) — server; TypeScript 5.7 (browser target, ESM) — client
**Primary Dependencies**: `effect` v3+, `@modelcontextprotocol/sdk` 1.29+, `@colyseus/core` 0.15.57, `colyseus.js` (client), `jsonwebtoken`, `@relateby/pattern`, React 18, Vite 6
**Storage**: No new storage; uses existing Neo4j ledger (via LedgerService) and in-memory Colyseus room state
**Testing**: `vitest` (server unit tests); Playwright (client e2e, existing); ghost-TCK (contract tests, needs live server)
**Target Platform**: Browser (client) + Linux server (world-api, colyseus, npc-agent)
**Project Type**: Web service (server changes) + browser application (client changes)
**Performance Goals**: Guest token issuance < 100ms; contract list poll < 500ms p95
**Constraints**: Must not break existing ghost MCP tool flows; Colyseus schema changes require coordinated deploy of server/colyseus + client
**Scale/Scope**: ~500 concurrent fair attendees; all actors share one Colyseus room

## Implementation Phases

### Phase A — Server: JWT role claim + guest token endpoint

**Deliverable**: A human client can obtain a valid JWT and make authenticated MCP calls.

**Files**:

1. **`server/world-api/src/jwt.ts`** — Add `role?: string` to `GhostClaims`:
   ```
   export interface GhostClaims {
     sub: string
     ghostId: string
     role?: string          // ← NEW; "human" for guest tokens
     caretakerId?: string
     agentHostId?: string
     agentId?: string
   }
   ```

2. **`server/world-api/src/auth-context.ts`** — Extract `role` from verified claims and add to `extra`:
   ```
   extra: {
     ghostId: claims.ghostId,
     role: claims.role,       // ← NEW
     caretakerId: claims.caretakerId,
     agentHostId: claims.agentHostId,
     agentId: claims.agentId,
   }
   ```
   The spawn-grant code at `mcp-server.ts:2255` already reads `authExtra?.role` — this change wires it correctly for humans without touching the spawn-grant logic.

3. **`server/world-api/src/guest-auth-route.ts`** (new file) — `POST /auth/guest`:
   - Accept `{ ghostId: string }` in request body
   - Validate: ghostId must be a non-empty string (≤128 chars)
   - Call `mintGhostToken({ sub: ghostId, ghostId, role: "human" })` with default 8h TTL
   - Return `{ token: string }`
   - No rate limiting (IAP is the perimeter)
   - Register route in world-api's h3 server setup

**Tests**: Unit test for `guest-auth-route.ts` — valid ghostId returns token with `role: "human"` in decoded claims; missing/invalid ghostId returns 400.

---

### Phase B — Server: ConversationService proximity exemption

**Deliverable**: Human callers can send directed `say()` without a world position.

**Files**:

1. **`server/conversation/src/ConversationService.ts`** — Add `callerRole?: string` to `say()` signature:
   ```typescript
   say(
     ghostId: string,
     content: string,
     to?: string,
     displayName?: string,
     intent?: string,
     callerRole?: string,   // ← NEW
   ): Effect.Effect<SayResult, ConversationStoreUnavailable | ConversationGhostNoPosition>
   ```

2. **`server/conversation/src/ConversationServiceLive.ts`** — Modify proximity check:
   ```typescript
   const rawCell = bridge.getGhostCell(ghostId)
   if (!rawCell && !(callerRole === "human" && to)) {
     return yield* Effect.fail(new ConversationGhostNoPosition({ ghostId }))
   }
   const ghostCell = rawCell ?? ""   // human directed: empty tile
   ```
   Broadcast path (no `to`): position check is unchanged — still fails for any caller without a position.

3. **`server/world-api/src/mcp-server.ts`** — In `sayEffect()`, extract role from `extra.authInfo` and pass to `conversation.say()`:
   ```typescript
   const callerRole = (extra.authInfo?.extra as any)?.role as string | undefined
   yield* conversation.say(ghostId, content, resolvedTo, displayName, intent, callerRole)
   ```

**Tests**: Unit test `ConversationServiceLive` — directed say with `callerRole: "human"` and no position succeeds; broadcast say with `callerRole: "human"` and no position fails with `ConversationGhostNoPosition`; ghost with position unaffected in both cases.

---

### Phase C — Server: Colyseus ghost labels

**Deliverable**: Client can identify broker ghosts from room state.

**Files**:

1. **`server/colyseus/src/room-schema.ts`** — Add to `WorldSpectatorState`:
   ```typescript
   @type({ map: "string" })
   ghostLabels: MapSchema<string> = new MapSchema<string>()
   // ghostId → comma-separated character gram labels, e.g. "Character:Broker"
   ```

2. **`server/colyseus/src/MatrixRoom.ts`** — On ghost join message that includes labels, set `state.ghostLabels[ghostId] = labels`. On ghost leave, delete the entry.

3. **`ghosts/npc-agent/src/`** (entry point) — When joining the Colyseus room, send labels derived from the character gram (`Character:Broker`, etc.) as part of the join payload or a subsequent room message.

**Tests**: Integration test (needs running Colyseus room) — NPC ghost join populates `ghostLabels`; ghost leave clears it.

### Phase D — Map gram: human role grants

**Deliverable**: Human clients receive starting broker-credits on first MCP connect.

**Files**:

1. **`maps/*.map.gram`** — Add `human` role to existing `:Grants` blocks:
   ```gram
   [:Grants { attendee: 10, human: 3, funder: 500 } | (goldCoin)]
   ```
   The exact grant amount is world-operator's decision; `3` is a starting suggestion for the broker-credit resource.

**Tests**: Verified by the spawn-grant idempotency acceptance test (SC-005) — inspect ledger after first and second human MCP connect.

---

### Phase E — Client: unified identity + JWT

**Deliverable**: Client has a stable ghostId, auto-generated editable display name, and valid JWT before any MCP call.

**Files**:

1. **`clients/intermedium/src/hooks/useIdentity.ts`** (new):
   - On mount: read `ghostId` and `displayName` from `localStorage`
   - If absent: generate ULID ghostId; generate display name via `unique-names-generator`; persist both
   - Fetch `POST /auth/guest` with `{ ghostId }`; store token in memory (not localStorage — avoid XSS)
   - Expose `{ ghostId, displayName, token, setDisplayName }` — `setDisplayName` persists to localStorage and marks name as "edited" (one-time lock)
   - On token expiry (8h), re-fetch silently

2. **`clients/intermedium/src/App.tsx`** — Wrap app in identity context; gate MCP calls until token is available.

**Tests**: Component test — first render generates ghostId and displayName in localStorage; second render reuses them; `setDisplayName` locks after one call.

---

### Phase F — Client: unified messaging

**Deliverable**: Human messages go through `say()` MCP tool; `/human-say` is retired from client.

**Files**:

1. **`clients/intermedium/src/hooks/useA2AConversation.ts`** — Replace `POST /threads/{ghostId}/human-say` with MCP `say` tool call using the guest JWT:
   ```typescript
   // POST /mcp with Authorization: Bearer <token>
   // body: { method: "tools/call", params: { name: "say", arguments: { content, to: ghostId, intent } } }
   ```

2. **`clients/intermedium/src/hooks/useColyseus.ts`** — Expose `ghostLabels` from room state per ghost.

**Tests**: Integration — send message to broker ghost; verify broker inbox receives it (requires live server).

---

### Phase G — Client: broker badge + contract UI + HUD balance

**Deliverable**: Broker ghosts are badged; contract flow is inline in chat; balance is visible in HUD.

**Files**:

1. **`clients/intermedium/src/components/GhostList/GhostList.tsx`** — Read `ghostLabels` from Colyseus state; render a "Broker" badge on ghosts whose labels include `"Character:Broker"`.

2. **`clients/intermedium/src/hooks/useContracts.ts`** (new):
   - Poll `eval_contract_list` MCP tool every 5s using guest JWT
   - Return `activeContract: EvalContract | null` — the first open/submitted contract where human is contractorId
   - Expose `submitAnswer(contractId, text)` — calls `eval_contract_submit` MCP tool

3. **`clients/intermedium/src/components/ChatPanel/ChatPanel.tsx`**:
   - When `activeContract` is non-null and selected ghost is the contract's clientId (broker), replace the chat input with a submission form: question text + textarea + submit button
   - On submit: call `submitAnswer()`; revert to normal input on success or settlement
   - Display "challenge expired" and revert input when contract state is `Expired`
   - Display "fully booked" message when broker responds with decline intent

4. **`clients/intermedium/src/components/HUD/BalanceDisplay.tsx`** (new):
   - Call `inventory` MCP tool on mount and after each contract settlement
   - Display broker-credit balance (resource label matching the `:Grants` item type)
   - Update within 5s of settlement (SC-003 proxy: leaderboard is 60s; balance is faster)

**Tests**: Component tests — broker badge renders when label present; contract form replaces input when activeContract set; balance updates after mock settlement.
